## 1. 專案概述

本系統為一套**純前端、可離線執行**的需求追蹤控管工具。使用者依 **EARS 四層架構**（User Story → EARS 需求 → BDD 情境 → 測試案例）輸入資料後，系統自動生成**需求追蹤控管表（Requirements Traceability Matrix, RTM）**，並提供覆蓋率儀表板與需求撰寫品質自我檢測。

### 核心特色
- 🔒 **100% 本地執行**：資料存於瀏覽器 IndexedDB，圖表以本地 ECharts 繪製，**不依賴外部 CDN、不需連網**。
- 🔑 **零金鑰**：不使用任何 API Key、Token 或憑證，無對外網路請求。
- 📊 **即時儀表板**：需求覆蓋率、狀態分布、優先度與 EARS 模式統計。
- ✅ **品質自我檢測**：依 EARS 撰寫檢核表自動評分並給出改善建議。
- 📱 **RWD 響應式**：寬螢幕水平選單，窄螢幕自動切換漢堡選單。

## 2. 目標與範圍

### 2.1 專案目標
| 目標 | 說明 |
|------|------|
| 需求可視化 | 將 EARS 四層需求以結構化控管表呈現，支援雙向追蹤 |
| 降低溝通落差 | 統一需求撰寫格式，涵蓋「可理解、可追蹤、可測試」 |
| 品質把關 | 提供自動化品質檢測，及早發現模糊或不完整的需求 |
| 免安裝、免部署 | 純前端檔案，雙擊即可開啟使用 |

### 2.2 範圍內（In Scope）
- 需求的新增、編輯、刪除、查詢、篩選
- 四層需求追蹤控管表生成
- 需求覆蓋率與狀態統計儀表板
- 需求撰寫品質自我檢測（單筆 / 批次）
- 資料 JSON 匯出 / 匯入備份

### 2.3 範圍外（Out of Scope）
- 多人協作、雲端同步（本版為單機瀏覽器儲存）
- 使用者帳號登入與權限管理
- 後端伺服器與資料庫
- 真實測試案例的自動執行（僅記錄測試案例編號與描述）

## 3. 技術架構

### 3.1 技術棧
| 層面 | 技術 | 說明 |
|------|------|------|
| 前端 | HTML5 + CSS3 + 原生 JavaScript (ES5/ES6) | 無框架、無建置流程 |
| 圖表 | ECharts（本地載入 `assets/echarts.min.js`） | 與 ECharts API 相容；可換官方完整版 |
| 資料儲存 | IndexedDB | 瀏覽器內建，資料庫 `rtm_db` / 物件倉 `requirements` |
| 樣式 | 自訂 CSS（CSS Variables + Flexbox/Grid） | 專業金融資訊系統藍調 |
| 響應式 | Media Query（斷點 860px / 480px） | 漢堡選單 |

### 3.2 架構特性
- **無後端**：所有邏輯在瀏覽器端執行。
- **無外部相依**：所有 JS/CSS/圖表資源皆為本地檔案。
- **無網路請求**：程式碼中不含 `fetch`、`XMLHttpRequest`、CDN 連結或外部 API 呼叫。

## 4. 功能規格

### 4.1 需求輸入（input.html）
- 依 EARS 四層架構填寫欄位（需求編號、User Story、EARS 模式與描述、BDD 情境、測試案例、類型、優先度、狀態、負責人）。
- 支援「新增」與「編輯」兩種模式（透過網址參數 `?id=` 進入編輯）。
- 提供「帶入範例」、「清空」、「即時品質檢測」輔助功能。
- 儲存後自動導向控管表。

### 4.2 控管表 RTM（matrix.html）
- 以表格呈現全部需求，橫向串接四層追蹤。
- 支援關鍵字搜尋（編號 / 描述 / 負責人）。
- 支援狀態、優先度下拉篩選。
- 每列可「編輯」、「刪除」。
- 支援「匯出 JSON」與「匯入 JSON」備份。
- 支援「清空全部」重置。

### 4.3 總覽儀表板（index.html）
- KPI 卡：需求總數、已對應測試案例數、測試覆蓋率、高優先度需求數。
- 覆蓋率量表（gauge）。
- 需求狀態分布（甜甜圈圖）。
- 優先度分布（長條圖）。
- EARS 模式分布（長條圖）。

### 4.4 品質自我檢測（checker.html）
- 可選擇既有需求或手動貼上內容檢測。
- 單筆檢測：顯示通過項目、得分、等級與改善建議。
- 批次檢測：一次評分所有需求並列出主要待改善項。

### 4.5 使用說明（guide.html）
- 啟動方式、頁面導覽、EARS 速記、技術架構、備份還原說明。

## 5. 資料模型

### 5.1 物件倉：`requirements`（IndexedDB）
主鍵 `id`（自動遞增），欄位如下：

| 欄位 | 型別 | 說明 | 範例 |
|------|------|------|------|
| `id` | number | 主鍵（自動遞增） | 1 |
| `reqId` | string | 需求編號（雙向追蹤主鍵） | `REQ-001` |
| `userStory` | string | 第 1 層 User Story | 身為…/我想要…/以便… |
| `earsMode` | string | EARS 模式 | 事件驅動 |
| `earsDesc` | string | 第 2 層 EARS 需求描述 | WHEN…，系統 SHALL… |
| `bdd` | string | 第 3 層 BDD 情境 | Given/When/Then |
| `tcId` | string | 第 4 層 測試案例編號 | `TC-001-01` |
| `testType` | string | 測試類型 | 正常 / 邊界 / 異常 |
| `priority` | string | 優先度 | 高 / 中 / 低 |
| `status` | string | 狀態 | 待分析/開發中/待測試/已核准/已完成/擱置 |
| `owner` | string | 負責人 | 姓名 / 工號 |
| `createdAt` | number | 建立時間戳 | 1721... |
| `updatedAt` | number | 更新時間戳 | 1721... |

### 5.2 列舉值（下拉選單常數）
- **earsMode**：普遍、事件驅動、狀態驅動、選用、異常
- **testType**：正常、邊界、異常
- **priority**：高、中、低
- **status**：待分析、開發中、待測試、已核准、已完成、擱置

## 7. EARS 需求規格（四層追蹤）

以下為系統內建的範例需求，示範四層雙向追蹤結構。

### REQ-001｜使用者登入（事件驅動）
- **User Story**：身為一般會員，我想要使用帳號密碼登入，以便存取個人服務。
- **EARS**：WHEN 使用者輸入帳號密碼並按下「登入」，系統 SHALL 驗證憑證是否與資料庫相符。
- **BDD**：Given 已註冊會員 / When 輸入正確帳密並登入 / Then 導向個人首頁。
- **測試案例**：`TC-001-01`（正常）｜優先度：高｜狀態：已核准

### REQ-002｜登入失敗提示（異常）
- **EARS**：IF 憑證驗證失敗，THEN 系統 SHALL 顯示「帳號或密碼錯誤」且不透露何者有誤。
- **BDD**：Given 已註冊會員 / When 輸入錯誤密碼 / Then 顯示錯誤訊息。
- **測試案例**：`TC-002-01`（異常）｜優先度：高｜狀態：開發中

### REQ-003｜帳號鎖定（異常 / 邊界）
- **EARS**：IF 連續 5 次登入失敗，THEN 系統 SHALL 鎖定帳號 15 分鐘。
- **BDD**：Given 已連續失敗 4 次 / When 第 5 次仍錯誤 / Then 鎖定帳號 15 分鐘。
- **測試案例**：`TC-003-01`（邊界）｜優先度：中｜狀態：待測試

### REQ-101｜LTV 自動檢核（事件驅動）
- **User Story**：身為授信審查人員，我想要系統自動檢核 LTV，以便符合授信規範。
- **EARS**：WHEN 授信案件送審，系統 SHALL 計算擔保品 LTV 比率。
- **BDD**：Given 估價 1000 萬、貸放 750 萬 / When 案件送審 / Then 計算 LTV=75% 並標記需覆核。
- **測試案例**：`TC-101-01`（正常）｜優先度：高｜狀態：已核准

### REQ-102｜授權額度覆核（事件驅動 / 邊界）
- **EARS**：WHEN 核定金額超過分行授權額度，系統 SHALL 將案件送交區域授信中心覆核。
- **BDD**：Given 核定金額超過授權 / When 案件送審 / Then 轉送區域授信中心。
- **測試案例**：`TC-102-01`（邊界）｜優先度：高｜狀態：開發中

### REQ-104｜估價資料缺漏阻擋（異常）
- **EARS**：IF 擔保品估價資料不存在，THEN 系統 SHALL 禁止案件送審並提示補件。
- **BDD**：Given 未上傳估價報告 / When 承辦嘗試送審 / Then 阻擋並提示補件。
- **測試案例**：`TC-104-01`（異常）｜優先度：高｜狀態：待測試

## 8. 品質檢測規則

系統依下列 9 項規則對每條需求評分，回傳「通過 / 未通過」與改善建議：

| # | 檢核項目 | 判定條件 |
|---|----------|----------|
| 1 | User Story 具備三要素 | 含「身為 / 我想要 / 以便」或標註同上 |
| 2 | 使用 EARS 觸發關鍵字 | 含 WHEN/WHILE/WHERE/IF（普遍需求例外） |
| 3 | 含系統行為關鍵字 SHALL | 描述含 `SHALL` |
| 4 | 異常需求 IF 搭配 THEN | 有 IF 則必須有 THEN |
| 5 | 單一需求只描述一個行為 | `SHALL` 出現次數 ≤ 1 且未包裹多重邏輯 |
| 6 | 條件可量化 | 含時間/次數/比率等數字（普遍需求例外） |
| 7 | 避免模糊字眼 | 不含「快速、盡量、最好、友善…」等 |
| 8 | 具備完整 BDD 情境 | 同時含 Given / When / Then |
| 9 | 對應至少一個測試案例 | `tcId` 不為空 |

**評分等級**：≥90% 優異｜≥70% 良好｜≥50% 待加強｜<50% 需重寫

## 9. 非功能性需求

| 類別 | 需求 |
|------|------|

## 10. 部署與執行

### 方式一（最簡單）
直接以瀏覽器開啟 `index.html`。

### 方式二（建議）
於專案資料夾啟動本機伺服器（避免部分瀏覽器對 `file://` 的限制）：
```bash
python -m http.server 8080
# 瀏覽器開啟 http://localhost:8080
```

### 資料備份
- **匯出**：控管表「⬇ 匯出 JSON」下載全部需求。
- **匯入**：「⬆ 匯入」選擇 JSON 附加匯入。
- 資料存於該瀏覽器 IndexedDB，換瀏覽器或清除瀏覽資料會遺失，請善用匯出備份。
